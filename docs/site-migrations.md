# Site Migrations

WP Wasmer includes a first-party migration flow for moving an existing WordPress site into a Wasmer WordPress app.

The system is split across two plugins:

- `wp-wasmer`
  Runs on the destination Wasmer WordPress app. It creates import sessions, accepts transferred content, stages files under `wp-content`, and applies the import.
- `wasmer-migrate`
  Runs on the source WordPress site. It parses an import code, exports the source database and content files, and transfers them to the destination in chunks.

## End-To-End Flow

1. An administrator opens the destination Wasmer WordPress app.
2. The destination creates an import session and returns a short-lived import code.
3. The administrator installs and activates `Wasmer Migrate` on the source WordPress site.
4. The source site connects to the destination with the import code.
5. The source site exports the database and scans selected `wp-content` assets.
6. The source sends a manifest to the destination.
7. The source transfers the database dump and files in bounded JSON/base64 chunks.
8. The destination verifies sizes and hashes, then marks the transfer complete.
9. A destination administrator starts the import.
10. The destination imports the database, copies staged content into `wp-content`, validates active dependencies, and marks the session complete.

The destination does not rely on PHP multipart upload temp files. Incoming chunks are written into persistent storage under `wp-content/wasmer-import`.

## Destination Plugin

The destination implementation lives in `wasmer/migrate-import/` and is loaded by the auto-installed `wp-wasmer` plugin.

Import data is stored under:

```text
wp-content/wasmer-import/
  sessions/
    <session>.json
  <session>/
    db/
    files/
    logs/
```

The destination writes access guard files into migration storage directories, including `index.php`, `.htaccess`, `web.config`, and `.user.ini` where applicable.

### REST Routes

Import routes are registered under the `wasmer/v1/import` namespace:

```text
POST /session
GET  /session/<id>
POST /session/<id>/connect
POST /session/<id>/manifest
POST /session/<id>/chunk
POST /session/<id>/complete
POST /session/<id>/start-import
POST /session/<id>/cancel
```

Admin-only routes require `manage_options`:

- `POST /session`
- `GET /session/<id>`
- `POST /session/<id>/start-import`
- `POST /session/<id>/cancel`

Source-to-destination transfer routes are public WordPress REST routes, but they authenticate with the import session token:

- `POST /session/<id>/connect`
- `POST /session/<id>/manifest`
- `POST /session/<id>/chunk`
- `POST /session/<id>/complete`

## Import Codes

An import code is generated by the destination and pasted into the source site.

The code format is:

```text
wasmer-import:v1:<base64url-json>
```

The decoded payload contains:

```json
{
  "v": 1,
  "target": "https://example.wasmer.app",
  "rest": "https://example.wasmer.app/wp-json/wasmer/v1/import",
  "session": "wmi_...",
  "token": "...",
  "expires": 1782920000,
  "app_id": "..."
}
```

The destination stores only a hash of the token. Transfer requests authenticate with:

```text
Authorization: WasmerImport <session>:<token>
```

The destination rejects unknown sessions, cancelled sessions, expired sessions, and requests with invalid token hashes.

## Source Plugin

The source implementation lives in `wasmer-migrate/`.

When a migration starts, the source plugin:

- parses and validates the import code;
- requires HTTPS for non-local destinations;
- connects to the destination session;
- exports the database to a local migration run directory;
- scans content files;
- builds a manifest;
- transfers the database and files;
- stores progress in WordPress state so CLI and admin flows can inspect or resume the migration.

The default content scan includes:

- `wp-content/uploads`
- `wp-content/themes`
- `wp-content/plugins`

The default scan excludes cache paths, backup paths, migration storage, `wp-wasmer`, symlinks, logs, temporary files, and partial files.

## Manifest

Before chunk transfer starts, the source sends a manifest describing the source site and expected payload:

```json
{
  "version": 1,
  "source": {
    "site_url": "https://old-site.example",
    "home_url": "https://old-site.example",
    "wp_version": "6.x",
    "php_version": "8.x",
    "table_prefix": "wp_"
  },
  "database": {
    "tables": [],
    "size": 123456,
    "sha256": "..."
  },
  "files": [
    {
      "path": "wp-content/uploads/2026/01/image.jpg",
      "size": 12345,
      "mtime": 1782920000,
      "sha256": "..."
    }
  ],
  "file_count": 1,
  "total_size": 135801,
  "options": {
    "include_uploads": true,
    "include_themes": true,
    "include_plugins": true,
    "include_mu_plugins": false
  }
}
```

The manifest also includes preflight data about the active source theme and active source plugins. The destination uses that data to warn or fail before import if required active dependencies are missing.

## Chunk Transfer

The source transfers files through `POST /session/<id>/chunk`.

Each request contains:

```json
{
  "kind": "file",
  "path": "wp-content/uploads/example.jpg",
  "offset": 0,
  "data": "base64-encoded chunk data",
  "sha256": "chunk hash"
}
```

The final chunk for a file also includes:

```json
{
  "final_size": 12345,
  "final_sha256": "full file hash"
}
```

The destination enforces the session chunk limit, validates paths, writes only inside the session staging directory, and verifies final file size and hash.

Default destination limits are filterable:

- `wasmer_import_max_chunk_size`, default `1048576`
- `wasmer_import_max_total_size`, default `21474836480`

## Import Execution

After transfer completion, the destination import process:

1. verifies the session and manifest;
2. verifies transferred database and files;
3. imports the source database through staging and backup table prefixes;
4. preserves destination-specific Wasmer settings;
5. copies staged `wp-content` files into the destination content directory;
6. preserves the destination `wp-wasmer` plugin activation;
7. removes `wasmer-migrate` from the imported active plugin list;
8. validates active plugin and theme files;
9. runs WordPress database upgrade routines when needed;
10. marks the session complete or failed.

WordPress core files are not migrated. Wasmer continues to control the core WordPress runtime.

## WP-CLI

Destination commands are provided by `wp-wasmer`:

```bash
wp wasmer import session create --expires=8h
wp wasmer import session list
wp wasmer import session status <session>
wp wasmer import session revoke <session>
wp wasmer import start <session>
wp wasmer import cleanup --older-than=7d
```

Source commands are provided by `wasmer-migrate`:

```bash
wp wasmer-migrate connect '<import-code>'
wp wasmer-migrate plan
wp wasmer-migrate start
wp wasmer-migrate status
wp wasmer-migrate resume
wp wasmer-migrate cancel
wp wasmer-migrate auto --graphql-url=<url> --token=<token> --owner=<owner> --region=<region>
```

The admin screens and CLI commands share the same migration state and transfer implementation.

## Security Model

The migration system uses the following controls:

- destination session creation is admin-only;
- import codes are short-lived;
- token hashes are stored at rest instead of raw transfer tokens;
- transfer requests require the session token;
- non-local source connections require HTTPS;
- transfer paths are normalized and constrained to session storage;
- staged storage is guarded against direct web access where the server supports it;
- chunk and total transfer limits are enforced by the destination;
- cancelled and expired sessions cannot continue accepting transfer data;
- source state removes the raw token after transfer completion.
